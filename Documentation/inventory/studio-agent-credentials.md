## Bounded semantic findings

### Screenplay open and call effects
- `studio_screenplay_open` reads the event-model export through Core, then opens a session using the organisation from `IOrganizationContext` (`Mcp/Tools/ScreenplayTools.cs:47–76`). Opening is not a pure read: `ScreenplaySessionHost.Open` creates a scratch directory, writes the exported baseline files, starts an embedded Screenplay MCP server on a background thread over in-memory pipes, and lists its tools (`ScreenplaySessions/ScreenplayMcpSessions.cs:26–74`; `ScreenplaySessions/ScreenplayWorkspaces.cs:42–59`). The session registry also changes in-memory state; a subsequent open may expire and dispose idle sessions (`Mcp/Screenplay/OpenScreenplaySessions.cs:65–80,112–123`).
- `studio_screenplay_call` resolves the session by `(organisation, sessionId)`, matches the supplied tool name against that session's advertised tools, parses JSON arguments and invokes the function (`Mcp/Tools/ScreenplayTools.cs:91–122`; `Mcp/Screenplay/OpenScreenplaySessions.cs:80–88`). The registry key is organisation-scoped, not person-scoped: any credential for the same organisation that holds a session id can call or apply that session. This wrapper imposes no additional read-only/effect filter on the selected function; a tool appearing in the session list is not evidence of read-only admission. The wrapper itself does not submit a Core command, but the effects of every dynamically advertised embedded tool have not been enumerated here.
- Distinguish nested workspace apply from Studio persistence: `studio_screenplay_apply` snapshots the workspace and submits `ApplyWorkspaceChanges` through Core before closing the session (`Mcp/Tools/ScreenplayTools.cs:137–156`). That command invokes the change translator (`Core/Projects/Applications/Domains/EventModels/Workspace/ApplyWorkspaceChanges.cs:23–40`). Closing disposes the MCP client/streams and deletes scratch files; it is stateful cleanup, not a data read (`ScreenplaySessions/ScreenplayMcpSession.cs:59–87`). These paths do not establish person approval, delegation or a safe tool ceiling.

### Query reachability and caller boundary
- The MCP query-dispatch surface includes person-oriented queries, not just organisation models: `GetMyProfile`, `GetMyAvatar` and `MyDialogPreferences` appear in `Core.Api/Generated/StudioApiCatalog.Queries.g.cs:19–47`. `CatalogLookup.Query` searches that catalogue case-insensitively, and `PerformQuery` forwards the selected route and supplied arguments without a per-query admission filter (`Mcp/Tools/CatalogLookup.cs:32–34`; `Mcp/Tools/CatalogTools.cs:169–180`). This establishes a reachable dispatch path to those routes, not that Core authorizes a request or returns a person's data.
- The profile query's result includes email, names, display name and biography, but selects the profile from `IStudioIdentityAccessor.GetCurrent().UserId`, not a caller-supplied profile identifier (`Core/Accounts/Profile/MyProfile/MyProfile.cs:17–39`). Avatar and dialog-preference queries likewise resolve the current identity server-side (`Core/Accounts/Profile/Avatar/Avatar.cs:34–37`; `Core/Accounts/Profile/Dialog/DialogPreferences.cs:31–34` and its helper `Core/Accounts/Profile/Dialog/DialogPreferencesObservation.cs:12–22`). Catalogue membership must not be described as arbitrary access to another person's profile.
- The MCP-to-Core seam issues an HTTP GET and stamps the current organisation, credential client id and forwarded principal (`Mcp/Api/StudioApi.cs:112–150,183–192`). `OrganizationContext.Current` derives that organisation from the forwarded principal and takes the client id from the forwarded subject header, falling back to the principal user id (`Mcp/Tenancy/OrganizationContext.cs:74–93`). These are the source-level handoff points, not independent proof of authenticated transport, current membership or person identity. The resulting Core identity/authorization decision and returned data under an organisation credential were not exercised; no exposure or successful person-data access is claimed.

## Gaps / could not determine
- Client-id header provenance (security, UNVERIFIED): `OrganizationContext` copies the client id from the incoming `x-ms-client-principal-id` header and `StudioApi` forwards it to Core unchanged (`Mcp/Tenancy/OrganizationContext.cs:87–91`; `Mcp/Api/StudioApi.cs:190`). Core reads that header in `Core/Settings/Users/TenantAccess/TenantSelection.cs:33`. The code comment at `OrganizationContext.cs:54–57` states only that spoofed `x-ms-client-principal` copies are stripped; whether the AuthProxy strips or overwrites a caller-supplied `-id` header was not traced and must be before any decision relies on that value.
- Core's authorization and identity mapping for every generated command/query remain unenumerated; the bounded query trace above does not establish the behavior of all ~530 commands or all catalogue queries.
- The effects and enforcement of every dynamically advertised embedded Screenplay tool remain unenumerated. The open/call wrappers and persistence boundary above are traced, but not a complete nested-tool safety audit.
- Successful authorization and data returned by the named account queries under an organisation MCP credential remain unverified. A person-oriented query in the reachable catalogue is not proof of disclosure.
- Frontend (TS/TSX) was searched; no organisation credentials are held in the browser code. Generated proxy files were not read in detail.
- Deployment code (`Deployment/Program.cs`, `Deployment/Networking/AuthProxyDeployment.cs`) was only searched for the credential verification path, not audited for secret handling.
- Chronicle/Mongo connection settings and the identity set at `Core/Program.cs:105-132` were read at overview level only.
- Other Cratis repositories (Chronicle, Arc, AuthProxy) were out of scope.
