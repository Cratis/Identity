# Internal client administration

Client registration, exact redirect replacement, secret rotation, and retirement are internal Arc commands. Like the existing account-linking commands, they are excluded from endpoint/proxy discovery. This increment does not connect the facts to OpenIddict stores or add an HTTP endpoint. Every command requires the authenticated, explicitly configured issuer security owner policy.

`AddClients()` binds `Identity:ClientSecrets:Key` and `Identity:ClientSecrets:Revision`. Supply the key through protected server configuration, never through a client command. The key must be base64-encoded and contain at least 32 bytes; the revision must be positive. There is no development fallback. Keep this key separate from upstream lookup and token-signing keys. Changing key material requires changing the revision and retaining the old key in the future verification boundary for any retained digest that must still be verified. This increment produces digests; it does not implement that verifier or key-ring management.

The producer computes HMAC-SHA-256 over UTF-8 `cratis.identity.client-secret.v1`, a NUL separator, and the command secret. The stored form is `v<revision>.<unpadded base64url digest>`, as required by `SecretDigest`. Plaintext is marked `NotAudited`, command `ToString()` is redacted, and events and read models contain only non-redeemable secret references and keyed digests. Do not log or serialize command objects as diagnostic payloads.

Confidential registration returns `ClientRegistered`, `ClientRedirectUrisChanged`, and the initial `ClientSecretRotated` in one batch on a generated registration stream. Public registration has no secret fact. `ClientRegistrationRules` remains the redirect/PKCE/native-client validation boundary. The client-id event constraint reserves each exact id permanently, including after retirement.

The dependency-free `ClientRegistrationReducer` folds Internal facts. Mutations read its state under Arc read protection and refuse absent or retired clients. A rotation cannot precede the current activation or place the old-secret deadline before the new activation; equal deadlines mean no overlap. Retirement uses the closed `owner_retired` reason rather than caller-provided text.
